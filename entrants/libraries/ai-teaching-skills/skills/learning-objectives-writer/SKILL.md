# Learning Objectives Writer

> If `teaching-context.md` exists, read it first, follow its house rules, and don't ask for anything it already answers.

An objective is only useful if you can see, by the end of the lesson, whether each student met it.

## Steps

1. **Start from the source.** Quote the specification point (board, code, reference). Don't add content the spec doesn't ask for at this level.
2. **Pick the level** with a verb you can observe:
   - *Know*: state, define, identify, label
   - *Understand*: explain, describe, compare
   - *Apply*: calculate, use, solve, write (code, a paragraph)
   - *Analyse and evaluate*: justify, assess, critique, decide

   Avoid "understand", "know about" or "appreciate" on their own: you can't see them happen.
3. **Write 2 or 3 objectives per lesson**, rising in difficulty, and no more than one lesson can achieve.
4. **Add success criteria** for each: the 2 to 4 things a strong answer contains. These become the marking points and the student checklist.
5. **Write a student version** in plain language: "By the end, you can explain why RAM is volatile and give two uses of ROM."
6. **Add the check**: the one question (hinge or exit ticket) that proves each objective was met.

## Output

| Objective (teacher) | Student version | Success criteria | How we'll know |
|---|---|---|---|

Keep the spec reference beside each objective so coverage can be tracked.
